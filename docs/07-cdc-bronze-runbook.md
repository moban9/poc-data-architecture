# Bronze CDC path — runbook

The only supported way data reaches `lakehouse.bronze` is:

```
LMS Postgres → Debezium (pgoutput) → Kafka (lms.public.*) → Iceberg sink → Polaris → MinIO/S3
```

Never populate bronze any other way. Writing Parquet/Iceberg files into the bucket
(or `INSERT`ing through Trino) bypasses the catalog, produces table locations that
Polaris does not know about, and leaves "rows" that the sink will never see.

## Verify the path is alive (60 seconds)

```bash
# 1. Both connectors must be RUNNING
curl -s localhost:8083/connectors/iceberg-sink/status
curl -s localhost:8083/connectors/debezium-postgres/status

# 2. Inject N loans and count bronze before/after
docker exec -e JAVA_TOOL_OPTIONS= lms-monitoring-trino-1 \
  trino --user keel --execute "SELECT count(*) FROM lakehouse.bronze.loan"
curl -s -X POST "localhost:8000/generate?count=7&mode=clean"
#    … wait ~2 commit cycles (commit interval is 10s, but a freshly started
#    task needs one cycle to load tables, so allow ~90s) …
docker exec -e JAVA_TOOL_OPTIONS= lms-monitoring-trino-1 \
  trino --user keel --execute "SELECT count(*) FROM lakehouse.bronze.loan"
```

The count must move by exactly N. The commit log is the audit trail:

```bash
docker logs lms-monitoring-connect-1 --since 5m 2>&1 | grep 'committed to'
# → "Commit … complete, committed to 2 table(s)"   = data committed
# → "committed to 0 table(s)"                      = nothing was flushed this cycle
```

## Failure mode 1 — sink RUNNING but commits 0 tables

Symptoms: connector and task `RUNNING`, consumer lag 0, `committed to 0 table(s)`
every cycle, and **no requests to Polaris from the Connect container**.

Cause: static routing drops records silently. With
`iceberg.tables.route-field=_cdc.target` and per-table `route-regex`, a record is
written only if the route value is non-null *and* matches a table regex. A task
that is running with a config from before the `transforms.unwrap.*` /
`route-field` settings took effect finds no `_cdc.target` and discards every
record without logging anything.

Fix / prevention:

```bash
curl -s -X POST "localhost:8083/connectors/iceberg-sink/restart?includeTasks=true"
```

then re-run the verify block. After any `PUT /connectors/iceberg-sink/config`,
confirm the task actually restarted and that Polaris starts receiving
`GET /namespaces/bronze/tables/...` requests from the Connect IP:

```bash
docker logs lms-monitoring-polaris-1 --since 5m 2>&1 | grep "$(docker inspect -f \
  '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' lms-monitoring-connect-1)"
```

## Failure mode 2 — 401 "Failed to verify token"

Symptoms: Polaris access log shows `Failed to verify token` + 401 for Trino/dbt/the
sink after a Polaris restart; Trino queries fail even though `Trino` is healthy.

Cause (two, both fixed in `compose/docker-compose.yml`):

1. **Ephemeral JWT signing keys.** Polaris generated a new RSA keypair at every
   boot, so every token issued before the restart stopped verifying.
   Fix: `polaris/keys/{private,public}.pem` generated by
   `compose/polaris/generate-keys.sh`, mounted at `/keys`, loaded through
   `-Dpolaris.authentication.token-broker.rsa-key-pair.*`. These must be `-D`
   system properties — the `POLARIS_AUTHENTICATION_TOKEN_BROKER_*` env vars bind
   to nothing (the config is a `@WithUnnamedKey` map) and fail silently.
   Verified by: issue a token, `docker restart` Polaris, reuse the same token → 200.
2. **In-memory metastore.** `polaris.persistence.type` defaults to `in-memory`, so
   every restart also deleted the `lakehouse` catalog and all bronze tables.
   Fix: `relational-jdbc` against `polaris-postgres`, with
   `?currentSchema=public` on the JDBC URL (without it the DDL bootstrap fails with
   `no schema has been selected to create in`) and
   `POLARIS_PERSISTENCE_AUTO_BOOTSTRAP_TYPES=relational-jdbc` so the schema is
   created on first boot.

Clients still hold a stale token until it expires — restart Trino once after
rotating keys, afterwards re-auth is automatic.

## Failure mode 3 — table created, rows never land

Check the commit cycle in the Connect log for
`received responses for 0 of 3 partitions`. A task that has just started must
join the `connect-iceberg-sink-coord` control group and load its tables before it
can answer `START_COMMIT`; the first one or two cycles time out and commit 0
tables. This is normal for ~90s after a start — do not "fix" it by restarting
again. If it persists for more than a few cycles, check:

```bash
docker exec -e JAVA_TOOL_OPTIONS= lms-monitoring-kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group connect-iceberg-sink
```

## Failure mode 4 — bronze row counts exceed distinct ids after a restart

Symptoms: `count(*)` is a multiple of `count(DISTINCT id)` (2.25x after one
crash-restart in the 2026-11-05 incident), `bronze.loan` above 354,360,
`dbt test` failing `unique_repayment_schedule_id` /
`relationships_loan_event_loan_id`, and dashboard KPIs inflated by the same
factor.

Cause: the sink is **at-least-once** — consumer offsets are committed after the
Iceberg commit, so a crashed or restarted task replays the uncommitted Kafka
window — and the Apache Iceberg Kafka Connect writer is **append-only**, so the
replay lands as duplicate rows. A blind `PUT /connectors/<name>/config` on every
`docker compose up -d` used to restart the task and provoke exactly that replay;
`register-connectors` now skips unchanged configs, so only real crashes replay.

Do **not** try to fix this with `iceberg.tables.upsert-mode-enabled` /
`iceberg.tables.cdc-field`. Those are Tabular-era keys: the Apache connector
(1.9.2 pinned here, and 1.12.0 too) does not define them and silently ignores
them. Evidence and the writer analysis: [09 §3](09-cdc-delivery-semantics.md).

What to do today:

```bash
./connectors/verify-idempotency.sh     # measures what a restart actually costs
```

With `EXPECT_IDEMPOTENT=1` it exits 2 on a dirty baseline (dedupe first: rename a
deduped copy into place — Polaris rejects table removal). In the default report
mode (`EXPECT_IDEMPOTENT=0`) a dirty baseline is reported and the run continues.
While the writer is append-only the script can only *quantify* the duplicates, not
pass; bronze is a changelog and the `unique_*` guarantees hold in silver
(`latest_cdc_row`, [09 §6.1](09-cdc-delivery-semantics.md)). The decision —
dedupe-on-read, approved — is [09 §5](09-cdc-delivery-semantics.md).

## Failure mode 5 — bronze rows grow past the source after a connector recreate

Symptom: `count(*)` in a bronze table is a multiple of the source row count, the
copies-per-id distribution is *uneven* (some ids 2x, some 20x+, most 1x), and the
Kafka topic's LOG-END-OFFSET equals the bronze row count — i.e. the sink wrote
every record exactly once and the **source** emitted the duplicates.

Cause: `snapshot.mode=initial`. Debezium snapshots when it has no stored offsets.
If a connector is recreated (or crashes repeatedly before its snapshot completes),
every restart re-emits the table from the first row again. Measured 2026-11-05:
`bronze.repayment_schedule` reached 14,347,023 rows for 6,908,334 source rows,
with 46 copies of the earliest ids and a 4.9x burst inside one hour.

Prevention (in place): the source template uses `SNAPSHOT_MODE` defaulting to
`no_data`, so a recreate resumes from the WAL and emits no history. Verify:

```bash
curl -s localhost:8083/connectors/debezium-postgres/config | grep snapshot.mode  # no_data
# then recreate the connector and confirm the topic end-offset does NOT move:
for t in loan loan_event repayment_schedule borrower; do
  docker exec -e JAVA_TOOL_OPTIONS= lms-monitoring-kafka-1 \
    /opt/kafka/bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 \
    --topic lms.public.$t --time -1
done
```

`snapshot.mode=no_data` means a **brand-new** environment gets no data rows on
first start: bootstrap it with
`SNAPSHOT_MODE=initial ./register-connectors.sh debezium-postgres`, or run
`resnapshot.sh` (the only entry point that opts into `initial` on purpose).
The rows already duplicated in bronze are not repaired by this — that is the
bronze reconcile (rename-based dedupe, kanban `t_43530a0f`).

## Failure mode 6 — sink writes parquet but "Nothing to commit" after Kafka recreation

Symptom: after the Kafka cluster is recreated (fresh VM / deleted `connect`
volumes), the sink consumes everything (consumer lag 0), writes Parquet data
files to the object store, but `bronze.*` stays empty. The Connect log shows
`Nothing to commit to table bronze.<t>, skipping` on every data cycle while
`committed to N table(s)` still prints, and no new Iceberg snapshots appear.

Cause: apache/iceberg #15293 (iceberg-kafka-connect 1.9.2). The sink's
committed data-topic offset is persisted in the Iceberg snapshot summary under
the key `kafka.connect.offsets.<control-topic>.<group>` (e.g.
`kafka.connect.offsets.control-iceberg.connect-iceberg-sink={"0":51767}`). When
Kafka is recreated the topics reset to offset 0, but that stale committed offset
still outranks every new record, so the coordinator dedupes them all. It is NOT
a table property (Trino `$properties` won't show it) and TRUNCATE/DROP does not
clear it (Polaris cannot DROP tables, and TRUNCATE keeps the snapshot history).

Fix / prevention: change `iceberg.control.topic` to a fresh name. The committed
offset key embeds the control-topic name, so a new name makes the coordinator
start with no committed offset and commit everything again.

```bash
# 1. stop the sink and give the control topic a new identity
curl -s -X DELETE localhost:8083/connectors/iceberg-sink
sed -i 's/"iceberg.control.topic": "[^"]*"/"iceberg.control.topic": "control-iceberg-v<N>"/' \
  compose/connectors/iceberg-sink.json
# 2. drop the stale control topic + consumer groups
docker exec -e JAVA_TOOL_OPTIONS= lms-monitoring-kafka-1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka:9092 --delete --topic control-iceberg
# 3. re-register
bash compose/connectors/register-connectors.sh iceberg-sink
```

The proper long-term fix is an iceberg-kafka-connect upgrade that includes the
#15293 recovery (detect a reset control topic and self-heal). Bump the version
in `scripts/fetch-iceberg-jars.sh` rather than re-applying the rename.

## Known debris (do not copy)

* `bronze/borrower-<uuid>/…` objects in the `lakehouse` bucket are leftovers from a
  manual direct-load into S3, not a registered Iceberg table. They are invisible to
  the catalog and must not be treated as bronze data.
